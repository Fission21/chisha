# ADR 制度说明

本项目使用 ADR（Architecture Decision Record，架构决策记录）管理重要技术决策。

## 什么是 ADR

ADR 是一篇独立、有日期、有状态、可检索的决策文档，回答四个问题：

- 我们面对的核心问题是什么？
- 有哪些可行方案？
- 为什么选择当前方案、为什么不选其他方案？
- 这个选择会永久带来哪些约束，如何验证它确实有效？

## 什么时候必须写 ADR

1. 新增、替换或移除核心技术组件。
2. 修改跨模块的 API、数据库表、数据结构或基础设施。
3. 存在多个候选方案，需要选择其中一个。
4. 形成长期执行的工程规则或架构约束。
5. 出现需要长期防止再次发生的重大问题。
6. 可能影响性能、安全、数据一致性、扩展性或部署方式的重大改造。

简单判断标准：如果半年后团队仍需要知道「当时为什么这么设计」，就应该写 ADR。

一次性 Bug、临时 workaround 和普通小修复，记录到 `ISSUES.md`，不写 ADR。

## 目录结构

```
decisions/
├── README.md        # 本文件，ADR 制度说明
├── INDEX.md         # ADR 总索引（每篇 ADR 必须登记）
├── _template.md     # ADR 模板
├── ISSUES.md        # 轻量问题记录
└── adr/
    └── YYYY-MM/
        └── YYYY-MM-DD-NNNN-short-title.md
```

## 命名与编号规则

- ADR 主文件放在 `decisions/adr/YYYY-MM/`，目录与文件名日期一致。
- 文件名：`YYYY-MM-DD-NNNN-short-title.md`，short-title 用英文小写短横线，不用中文、空格、下划线。
- `NNNN` 为四位数字编号，全局递增、跨月份不重置，不重复、不复用。
- 一篇 ADR 对应一个独立文件，不合并。
- ADR 目录中不放截图、日志、临时脚本或运行产物；大附件用同编号附属目录 `NNNN/`。
- 引用其他 ADR 用相对路径；引用项目代码用仓库根路径。

## 状态流转

| 状态 | 含义 |
|---|---|
| 草案 | 正在讨论，尚未生效 |
| 已采纳 | 决策已确认并开始执行 |
| 部分落地 | 决策已确认，但实现尚未完成 |
| 已废弃 | 被新 ADR 替代 |
| 已复盘 | 运行一段时间后补充了实际效果 |

已采纳的 ADR 不允许直接修改核心决策内容。方案变化时：新建 ADR → 声明替代旧 ADR → 旧 ADR 标记「已废弃」并链接新 ADR → 同步索引。

## 提交前检查

1. 编号没有重复、没有断层（缺号需记录原因）。
2. 文件名符合规范。
3. 状态合法。
4. ADR 已登记到 `INDEX.md`。
5. 相关代码、测试和文档链接有效。

## 写作要求

不要写成开发流水账。重点回答：核心问题、可行方案、选择理由、不选理由、长期约束、验证方式、何时需要重新决策。
