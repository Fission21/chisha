# ADR-0003：规则打分推荐算法

- 状态：已复盘
- 日期：2026-08-04
- 决策人：项目作者（CC）
- 标签：#推荐算法 #规则引擎 #可解释性 #MVP
- 关键词：规则打分、热量匹配、多样性、AI 推荐、可解释

## 1. 背景

产品核心链路是「营养目标 → 吃什么」：根据用户身体档案和目标（增肌 / 减脂 / 维持），按早餐 / 午餐 / 晚餐 / 加餐各推荐若干道菜谱。方案选择直接影响推荐质量、可解释性、性能与后续演进。

需要决策：用什么方式做推荐？候选有规则打分、协同过滤、基于 LLM 的推荐等。MVP 阶段实现为规则打分（`api/app/recommend.py`），本 ADR 记录该决策。

## 2. 目标与边界

### 目标

- 推荐结果符合营养目标：热量、蛋白质匹配是硬指标。
- 遵守硬性约束：过敏原 / 忌口必须排除，菜系偏好可过滤。
- 每餐推荐「任选其一即可达标」，避免用户误读为套餐合计。
- 推荐逻辑可解释：能说出「为什么推荐这道菜」。
- 支持单日推荐与一周餐单（7 天尽量不重复）+ 购物清单汇总。

### 不在本次范围内

- 不做基于用户行为历史的个性化（无用户行为数据基础）。
- 不做实时学习 / 模型训练。
- 不做 AI 菜谱生成（V2/V3 预留，见 `PRODUCT.md` 待定项）。
- 不做评分 / 反馈数据采集来优化推荐。

## 3. 候选方案

### 方案 A：规则打分（权重线性加权）

`score = 0.45×热量匹配 + 0.30×蛋白质匹配 + 0.15×目标标签匹配 + 0.05×菜系偏好 + 0.05×多样性`，先硬性过滤过敏原，按餐分别打分取 Top 3。

- 优点：实现简单（约 120 行，无外部依赖）；完全可解释；性能极快（77 道菜全量打分毫秒级）；确定性可测试。
- 缺点：权重需人工调优；无法捕捉隐含偏好；多样性只做「避免同菜系连续」的轻量处理。
- 成本：权重调优 + 测试，MVP 阶段已覆盖（后端自动化测试）。
- 风险：推荐效果的天花板受限于人工权重，长期可能不够「聪明」。

### 方案 B：协同过滤 / 矩阵分解（基于用户行为）

- 优点：随用户行为数据增长，个性化能力持续提升。
- 缺点：冷启动问题（新用户无行为）；当前用户行为数据几乎为零；可解释性差。
- 成本：数据采集管道 + 模型训练 + 推荐服务，复杂度高。
- 风险：数据量不足时效果不如规则法。

### 方案 C：LLM 推荐（基于大模型的语义推荐）

- 优点：语义理解强，可自然语言交互（「今天想吃辣的」）。
- 缺点：延迟、成本、不确定性与幻觉（营养数据必须精确，幻觉不可接受）；需要外部 API 或本地部署。
- 成本：API 费用 + 提示工程 + 幻觉防护。
- 风险：营养计算必须精确，LLM 输出不可靠；与「先算对再推荐」的产品原则冲突。

## 4. 最终决策

最终选择：方案 A（规则打分）。

核心理由：

1. 产品原则「先算对，再推荐」（`PRODUCT.md` 原则 1）：营养匹配是硬指标，规则法直接可计算、可验证。
2. 数据规模小（77 道菜谱），规则法全量打分即可获得足够质量，ML 方案没有数据支撑。
3. 可解释性：每个分数来自明确权重，调试与调优成本低。
4. 确定性：同一输入永远同一输出，测试友好（`api/tests/` 覆盖推荐逻辑）。

为什么不选择其他方案：

- 方案 B：无行为数据基础，冷启动不可解，MVP 阶段收益为负。
- 方案 C：幻觉风险直接破坏「营养数据精确」的产品底线；成本与延迟不可接受。

## 5. 架构与实现约束

- 推荐入口：`api/app/recommend.py` 的 `recommend()`（单日）与 `recommend_week()`（一周餐单），禁止绕过该模块在路由中另写推荐逻辑。
- 硬性过滤优先于打分：过敏原交集（`set(r.allergens) & set(allergies)`）直接排除；菜系偏好是过滤条件而非仅加分项（`recommend()` 中 `preferred_cuisines` 非空时先过滤）。
- 权重表 `0.45 / 0.30 / 0.15 / 0.05 / 0.05` 是长期默认值，调整必须同步更新本 ADR 的复盘记录或新建 ADR。
- 每餐输出固定结构：`meal / mealLabel / targetKcal / targetProtein / recommendations`（Top 3，`API` 契约见 `api/app/routers/plan.py`）。
- 一周餐单：整周尽量不重复（`used` 集合），重复兜底策略为「热量最接近」（`_pick_one` 兜底分支），购物清单按「食材 × 克数 / servings」聚合。
- 推荐输入输出必须纯函数化（无 IO），便于单元测试。

## 7. 验收标准

- `pytest api/tests -q` 全绿，推荐相关用例覆盖：过敏原排除、菜系偏好过滤、热量/蛋白质匹配、一周不重复、购物清单聚合。
- 同一输入重复调用输出完全一致（确定性）。
- 过敏原命中时该菜谱必不出现于任何推荐结果（硬性约束验证）。
- 每餐推荐 ≤ 3 道且标注「任选其一」。
- 一周餐单 7 天 × 4 餐，任意两天的同一餐不重复（菜谱数不足时允许兜底重复，逻辑在 `_pick_one` 中明确）。
- 推荐计算时间在数据规模扩大 10 倍后仍低于 100ms（纯计算，无 IO）。

## 8. 后果与风险

### 正面影响

- 推荐可解释、可测试、零外部依赖、零运行成本。
- 权重调整可以快速验证效果，迭代成本低。

### 负面影响和代价

- 推荐效果上限受人工权重限制，缺乏「意外惊喜」的个性化能力。
- 多样性只解决同菜系连续，不做更深层的内容多样性。
- 菜系偏好作为过滤条件会显著缩小候选集（菜谱仅 77 道时可能出现无推荐）。

### 持续跟踪风险

- [ ] 菜谱库扩到几百道后，权重是否需要重新调优。
- [ ] 用户行为数据积累后是否值得升级为方案 B（个性化）。
- [ ] 无推荐（候选为空）场景的用户体验与兜底策略。

## 9. 复盘

- 预期目标是否达成：达成。单日推荐与一周餐单上线即用，测试覆盖推荐核心约束。
- 实际收益和成本：规则实现约 120 行，零运行成本，调权快速。
- 哪些假设被证明错误：暂无。
- 是否需要新建 ADR 替代当前决策：需要时——若菜谱规模扩大导致规则法质量不足，或用户行为数据积累到可支撑个性化，再启动替代决策（候选为方案 B 或方案 A 的升级版）。
