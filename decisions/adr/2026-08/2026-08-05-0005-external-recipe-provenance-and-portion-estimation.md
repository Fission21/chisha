# ADR-0005：外部菜谱溯源与家庭份量估算

- 状态：已采纳
- 日期：2026-08-05
- 决策人：项目作者（CC）
- 标签：#数据 #版权 #菜谱 #营养 #用户体验
- 关键词：HowToCook、Unlicense、USDA FoodData Central、家庭份量、来源溯源

## 1. 背景

项目已有按克数计算营养的菜谱管道，但缺少两项能力：

1. 合规地引入外部的日式、西式做法，并让用户能查到每道菜的来源与固定版本。
2. 让用户用自然语言查询常见食材的份量，例如“大苹果”“中等香蕉”“250 ml 牛奶”。

不能把第三方菜谱正文或未经验证的“预估卡路里”直接混入现有营养库；也不能把“一个”一律假装成精确克数。

## 2. 目标与边界

### 目标

- 以可再利用、许可明确的上游内容扩展菜谱，并保存来源、许可证、固定版本与 URL。
- 保持“食材 × 克数”是每份营养的唯一计算路径。
- 提供有明确估算说明的家庭份量查询；无法可靠换算时提示用户补充克数。

### 不在本次范围内

- 不在运行期抓取、同步或依赖外部菜谱站点。
- 不批量导入未人工映射食材、非标准单位或权利链不清的语料。
- 不把份量估算表达为医疗建议，也不替代包装营养标签。

## 3. 候选方案

### 方案 A：HowToCook 固定快照 + 人工营养映射

- 优点：根 `LICENSE` 是 Unlicense；Markdown 做法清晰；可保留精确路径和提交 SHA。
- 缺点：不是结构化营养库；食材用量常有“个、适量、范围”等表达，不能全量自动导入。
- 风险控制：仅导入已经把食材映射为 g/ml 的菜谱，图片不导入。

### 方案 B：网页爬虫或无明确权利链的 GitHub 镜像

- 优点：数量大。
- 缺点：正文、图片与再分发权不清；无法保证食材和营养质量。
- 结论：不采用。

### 方案 C：运行期调用外部营养 API

- 优点：理论上数据新。
- 缺点：引入网络依赖、可用性和隐私边界，不符合单服务静态数据架构。
- 结论：不采用；仅在构建期或人工审校时参考公开数据。

## 4. 最终决策

选择方案 A，并把“菜谱内容来源”与“营养事实来源”分离：

1. 采用 `Anduin2017/HowToCook` 的 Unlicense 固定提交 `c05758fa661ac4efa0361a987b700a351a22159b`，首批人工整理 4 道日式/意式/西式菜谱。
2. 每个外部菜谱必须在源 JSON 中带 `source.name`、`source.url`、`source.license`、`source.revision`；构建产物、API、详情页都保留并展示该信息。
3. 任何上游“预估卡路里”只作参考，不进入计算；营养继续由本地食物表与明确 g/ml 数量推导。
4. `data/food_portions.json` 保存已审校的家庭份量规则。份量采用 USDA FoodData Central 的公共领域家庭份量口径作估算依据，结果必须标注“估算”。

## 5. 架构与实现约束

- 外部源文件只能放在 `data/recipes/*.json`，不得在运行期下载上游内容。
- `scripts/build_data.py` 必须验证所有 `ingredients[].ref`，并把来源对象写入 `data/processed/recipes.json`。
- `api/app/seed.py` 同步静态食材和菜谱，允许新增/刷新静态菜谱，但不得删除或改写用户档案、收藏、日记。
- `POST /api/foods/estimate` 最多处理 12 项；只接受显式重量/体积或配置过的家庭份量。未匹配项返回原因，不做模糊猜测。
- 外部图片、原文附带的第三方链接和未核验品牌营养信息不导入。

## 6. 验收标准

- 每道导入的 HowToCook 菜谱在 API 与静态详情页中显示可点击来源、Unlicense 和固定版本。
- 构建脚本可重复生成 `foods.json`、`recipes.json`、`food_portions.json`，且所有食材引用已解析。
- “一个大苹果，一个中等长度的香蕉，一杯 250 毫升的牛奶”能返回逐项克数、营养与合计。
- 未识别或未配置份量的输入明确提示补充信息。
- 完整后端测试、前端构建和浏览器交互验证通过。

## 7. 后果与风险

- 优点：外部内容可追溯、可复现，日式和西式菜谱扩充不破坏现有营养路径。
- 代价：全量导入仍需要人工映射与审校，不能以数量替代数据质量。
- 持续风险：食材表中的脚注、品牌差异、生熟重量和可食部都会影响结果；页面须继续保留估算说明和来源信息。
