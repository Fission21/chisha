# ADR-0006：外部菜谱按需分批扩充

- 状态：已采纳
- 日期：2026-08-05
- 决策人：项目作者（CC）
- 标签：#数据 #菜谱 #版权 #交付节奏
- 关键词：按需扩充、显式用户请求、分批验收、来源溯源、HowToCook

## 1. 背景

ADR-0005 已建立外部菜谱的来源、许可、固定版本、食材克重映射和营养重算规则。首批接入用于验证整条链路，不能被误解为“已完成菜谱库规模化扩充”。

项目当前有 81 道菜谱；用户已明确要求将来可以继续接入更多菜谱。若自动全量抓取或导入上游 Markdown，会绕过份量与营养校验，造成菜谱数量增长但数据质量不可控。

## 2. 目标与边界

### 目标

- 把“后续扩充菜谱”记录为由用户明确请求触发的持续能力，而不是一次性自动任务。
- 每次扩充都以可审计的批次交付，保持 ADR-0005 的来源、版权和营养质量边界。
- 让用户可按菜系、数量或来源指定下一批；未指定时，交付方应选择小而可核验的批次并如实报告范围。

### 不在本次范围内

- 不在没有用户请求时自动抓取、同步或批量导入第三方菜谱。
- 不预先承诺某个总菜谱数量、上线日期或特定菜系比例。
- 不放宽 ADR-0005 对固定版本、食材映射和营养计算的约束。

## 3. 候选方案

### 方案 A：立即全量自动导入上游仓库

- 优点：菜谱数量增长快。
- 缺点：上游 Markdown 的单位、可食重量和营养信息不统一，容易产生不可验证的结果。
- 结论：不采用。

### 方案 B：只在文档中保留模糊的扩充意向

- 优点：无需维护规则。
- 缺点：后续容易遗漏用户的产品方向，也没有可执行的质量门槛。
- 结论：不采用。

### 方案 C：用户触发、按批次人工核验后接入

- 优点：兼顾菜谱库扩充、版权边界和营养可信度；每批范围与效果可追溯。
- 缺点：需要持续的映射、构建和验收工作，数量增长不等同于一键导入。
- 结论：采用。

## 4. 最终决策

选择方案 C。未来当用户明确提出“接入更多菜谱”或给出菜系、来源、数量等范围时，将其视为对相应扩充批次的授权。

每个批次必须：

1. 明确本批次的来源、固定版本（如适用）、许可与菜谱数量。
2. 仅导入能映射到本地食物表、且每种食材具有明确 g/ml 用量的菜谱；无法可靠映射的菜谱不进入营养库。
3. 在 `data/recipes/` 保留来源字段，并经 `scripts/build_data.py` 重建生成数据。
4. 更新用户可见的菜谱数量与来源说明，执行与改动相称的后端、前端和浏览器验证。

## 5. 架构与实现约束

- 继续遵循 ADR-0005：不在运行期依赖外部站点，不导入第三方图片或权利链不清的内容。
- 新增菜谱不得改写用户档案、收藏或饮食记录；静态菜谱同步必须保持幂等。
- 每道外部菜谱必须保留 `source.name`、`source.url`、`source.license` 和 `source.revision`（存在固定版本时）。
- 若用户没有指定批次规模或菜系，先交付范围有限、可审校的一批，并在交付时报告实际新增数量与未纳入原因。

## 6. 验收标准

- 本 ADR 已登记在 `decisions/INDEX.md`，并与 ADR-0005 关联。
- 后续每个扩充批次均能列出新增数量、菜系、来源与许可。
- 新菜谱的食材引用和营养计算可由构建脚本及 API 验证。
- 用户界面显示的菜谱总数与运行中 API 返回总数一致。

## 7. 后果与风险

### 正面影响

- 用户可以持续扩充中式、日式、西式等菜谱，而不牺牲来源透明度和热量估算质量。
- 扩充范围由用户的实际优先级驱动，避免无用的大规模导入。

### 负面影响和代价

- 每批接入仍需人工审校，不能把数量当作质量替代品。
- 菜谱总数会随批次变化，文档和界面中的统计必须同步更新。
