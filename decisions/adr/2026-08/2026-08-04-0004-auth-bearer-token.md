# ADR-0004：认证与用户数据同步方案

- 状态：已复盘
- 日期：2026-08-04
- 决策人：项目作者（CC）
- 标签：#认证 #安全 #数据同步 #用户体系
- 关键词：PBKDF2、Bearer 令牌、JWT、OAuth、云端同步

## 1. 背景

产品需要「记住档案 + 换设备不丢」：注册 / 登录后，身体档案、收藏、饮食记录云端保存。MVP 前所有数据在 localStorage（`11edec5` 之前），无账号体系。

需要决策：认证方式（密码哈希算法、令牌机制）与用户数据存储边界。实现为：PBKDF2（100,000 次迭代）哈希密码 + 随机不透明 Bearer 令牌（`api/app/auth.py`），用户数据存 SQLite（`api/app/models.py` User/UserProfile/UserFavorite/UserDiary）。本 ADR 记录该决策。

## 2. 目标与边界

### 目标

- 密码不以明文 / 可逆形式存储，防拖库后直接泄露。
- 登录状态简单可撤销（令牌失效即可踢下线）。
- 实现不引入重依赖（无第三方 OAuth、无 JWT 库）。
- 用户数据模型覆盖：档案、收藏、饮食记录，且换设备可恢复。

### 不在本次范围内

- 不做第三方 OAuth 登录（微信 / Google）。
- 不做邮箱验证、找回密码、令牌刷新 / 过期时间策略。
- 不做多设备同时登录管理（单令牌模型，登录即替换）。
- 不做管理员后台与权限分级。
- 不做 HTTPS 强制（部署层职责，反向代理负责）。

## 3. 候选方案

### 方案 A：PBKDF2-SHA256（100k 迭代）+ 随机不透明 Bearer 令牌

密码哈希：`hashlib.pbkdf2_hmac("sha256", password, salt, 100_000)`，salt 随机 16 字节 hex，比较用 `secrets.compare_digest`。令牌：`secrets.token_urlsafe(32)` 明文存库，请求头 `Authorization: Bearer <token>` 查库匹配。

- 优点：零第三方依赖（标准库实现）；PBKDF2 有盐 + 高迭代，抗彩虹表与暴力破解；令牌随机 256 bit 不可猜测；撤销 = 删库中令牌，简单可靠。
- 缺点：令牌明文存库，库被拖走即可冒充在线用户（需要再拖一次库才有价值）；无过期机制，令牌永久有效直到换设备登录。
- 成本：标准库实现，约 30 行。
- 风险：令牌无过期是主要风险；密码强度依赖用户自觉。

### 方案 B：JWT（PyJWT 签发签名令牌）

- 优点：无状态（服务端不存令牌）；可带过期时间；生态成熟。
- 缺点：引入 JWT 库依赖；**撤销困难**（必须维护黑名单，否则只能等过期）；密钥管理责任落到应用层；复杂度与本项目规模不匹配。
- 成本：依赖 + 密钥管理 + 刷新机制。
- 风险：密钥泄露 = 任意签发令牌；撤销机制缺失时用户无法主动下线。

### 方案 C：第三方 OAuth（微信 / GitHub 登录）

- 优点：用户无需注册新账号；无密码存储责任。
- 缺点：需要第三方应用注册与回调配置；中文用户场景需微信生态，涉及资质；实现复杂度最高。
- 成本：第三方对接 + 回调 + 绑定逻辑。
- 风险：平台策略变化；MVP 阶段拖慢上线。

### 方案 D：无认证（仅 localStorage 客户端存储）

- 优点：最简单。
- 缺点：换设备 / 清缓存数据即丢失，与「记住档案、换设备不丢」的产品目标直接冲突。
- 成本：零。
- 风险：产品承诺无法兑现。

## 4. 最终决策

最终选择：方案 A（PBKDF2 + 不透明 Bearer 令牌）。

核心理由：

1. 与 ADR-0001 单服务、零配置架构一致：标准库实现，无新依赖。
2. 令牌可撤销、密码抗拖库，安全性对本项目数据（健身档案、菜谱收藏）足够。
3. 实现约 30 行，可测试可审计（`api/tests/` 覆盖认证流程）。
4. 避免了 JWT 的撤销难题与密钥管理责任。

为什么不选择其他方案：

- 方案 B（JWT）：撤销困难 + 密钥管理，换来的无状态对本单实例架构没有收益。
- 方案 C（OAuth）：复杂度与资质要求远超 MVP 收益。
- 方案 D（纯 localStorage）：直接违背产品目标。

## 5. 架构与实现约束

- 密码哈希：PBKDF2-HMAC-SHA256，迭代 100,000（`api/app/auth.py` `ITERATIONS`），salt 为 `secrets.token_hex(16)`，比较必须用 `secrets.compare_digest`，禁止用 `==`。
- 令牌：`secrets.token_urlsafe(32)`（256 bit），Bearer 方式传递；认证依赖 `get_current_user` 查 `users.token` 列，禁止绕过后端认证在前端校验权限。
- 单令牌模型：登录生成新令牌并覆盖旧令牌（旧设备自动下线），登出清空令牌。
- 用户数据边界：`UserProfile`（档案，唯一约束）、`UserFavorite`（收藏，`uq_user_fav` 唯一约束）、`UserDiary`（饮食记录，`uq_user_diary` 每日一条唯一约束）——见 `api/app/models.py`。
- 密码必须走哈希，禁止在日志、响应或前端存储中回传明文密码 / 哈希。
- 未登录用户保持 localStorage 本地模式，登录后合并 / 读取云端数据（前端实现，`web/lib/` 负责 API 调用）。
- 涉及认证的 API（`api/app/routers/auth.py`、`me.py`）必须依赖 `get_current_user`，接口契约保持向后兼容。

## 7. 验收标准

- `pytest api/tests -q` 全绿，认证用例覆盖：注册、登录、错误密码、未登录 401、登出、令牌覆盖。
- 数据库中密码字段无明文（仅 `password_hash` + `salt` 两列，格式可验证）。
- 注册后换设备（新请求）凭令牌可读取云端档案 / 收藏 / 饮食记录。
- 修改密码 / 重新登录后旧令牌立即失效。
- 同一用户收藏同一菜谱两次不产生重复行（唯一约束）。
- 前端未登录状态下全部功能仍可用（本地模式降级）。

## 8. 后果与风险

### 正面影响

- 零依赖、可撤销、可测试的认证实现，符合单服务架构。
- 用户数据云端同步兑现「换设备不丢」的产品承诺。

### 负面影响和代价

- 令牌无过期机制：泄露后长期有效（缓解：单令牌模型 + 重新登录即失效；长期应补过期策略）。
- 无邮箱验证与找回密码：用户忘记密码只能重新注册（当前接受）。
- 密码强度完全依赖用户（无策略强制）。

### 持续跟踪风险

- [ ] 令牌过期 / 刷新机制是否需要在用户规模增长后补充（当前单令牌 + 重登覆盖）。
- [ ] 是否出现暴力破解尝试（当前无限流，部署层需加，如反向代理限速）。
- [ ] 是否需要邮箱验证 / 找回密码（产品反馈中出现则评估）。
- [ ] HTTPS 部署时必须由反向代理强制（本 ADR 不负责部署层）。

## 9. 复盘

- 预期目标是否达成：达成。注册 / 登录 / 云端同步上线，测试覆盖核心认证路径。
- 实际收益和成本：约 30 行标准库实现，无新依赖，安全属性对项目数据规模充分。
- 哪些假设被证明错误：暂无。
- 是否需要新建 ADR 替代当前决策：需要时——若补充令牌过期 / 刷新机制、接入 OAuth、或引入限流作为正式安全基线，应新建 ADR 并废弃 / 关联本 ADR。
