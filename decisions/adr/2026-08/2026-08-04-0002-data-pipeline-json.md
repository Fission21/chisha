# ADR-0002：数据管道与数据源选型

- 状态：已复盘
- 日期：2026-08-04
- 决策人：项目作者（CC）
- 标签：#数据 #数据管道 #版权 #构建期
- 关键词：中国食物成分表、USDA、JSON、构建期数据、菜谱营养推导

## 1. 背景

产品核心依赖两类数据：食材营养（1741 条）与菜谱（77 道）。决策需要回答两个问题：

1. **数据从哪来**：营养数据必须有可追溯来源；菜谱需要覆盖中餐 + 全球做法；商用需考虑版权。
2. **数据怎么进入系统**：运行期查数据库，还是构建期生成静态 JSON。

MVP 之前已调研数据源（`docs/01-调研报告.md`、`docs/recipe-sources-research.md`）。数据管道定型为：`scripts/build_data.py` 读取 `data/raw/` 与 `data/recipes/`，产出 `data/processed/foods.json` 与 `data/processed/recipes.json`，`seed` 时导入 SQLite。本 ADR 记录数据源选型与「构建期 JSON 管道」两个决策。

## 2. 目标与边界

### 目标

- 营养数据可追溯到来源（中国食物成分表第 6 版 / USDA 近似值），不编造数据。
- 菜谱营养由「食材 × 克数」推导，食材库更新时菜谱营养自动正确。
- 数据更新路径简单：改 JSON → 跑 build → 重启，无需迁移脚本。
- 尊重版权：学习研究可用，商用路径明确（换开源数据或购买授权）。

### 不在本次范围内

- 不做运行期数据管理后台 / 在线编辑。
- 不做 USDA FDC API 运行期实时拉取（当前为静态近似值，需要时再接入）。
- 不做 AI 训练级菜谱数据（Food.com / Recipe1M / CNFOOD-241 为 V3 预留，本次不接）。

## 3. 候选方案

### 3.1 数据源选型

### 方案 A：中国食物成分表（第 6 版）+ 全球食材 USDA 近似值

- 优点：中文食材覆盖完整（1657+ 条）；来源权威；近似值数据标注 source 字段，诚实可追溯。
- 缺点：第 6 版数据版权归出版社，商用需授权；USDA 为近似值，非一一精确。
- 成本：一次抓取 / OCR 清洗（已有 raw 数据），后续按需补充。
- 风险：商用合规风险（需购买授权或换开源数据）；OCR 识别可能存在误差。

### 方案 B：仅 USDA FDC API

- 优点：完全开源、API 可运行期调用。
- 缺点：中文食材覆盖差（豆腐、酱油、皮蛋等大量中式食材缺失），与本产品「中餐为主」定位冲突；运行期依赖外部 API。
- 成本：需要大量映射与补充。
- 风险：中文食材缺口导致推荐失真。

### 方案 C：CNFOOD-241 等 AI 训练数据集

- 优点：面向 AI 训练，营养字段丰富。
- 缺点：为 V3 AI 功能预留，当前规则推荐用不上；数据格式与使用条款需另行评估。
- 成本：高，需额外数据清洗。
- 风险：提前引入复杂度。

### 3.2 数据进入系统的管道

### 方案 D：构建期静态 JSON（脚本生成 + seed 导入）

- 优点：数据定型于构建期，运行期只读；改动路径清晰（改 JSON → 跑 build）；无运行期数据依赖；与 ADR-0001 单服务架构契合。
- 缺点：新增菜谱需重新 build + 重启；数据版本与代码版本耦合。
- 成本：`scripts/build_data.py` 一次开发，后续按需维护。
- 风险：无。

### 方案 E：运行期数据库 + 迁移脚本管理

- 优点：数据与代码解耦，可运行期维护。
- 缺点：需要数据管理后台 / 迁移工具（Alembic），与「刻意保持简单」冲突。
- 成本：迁移工具 + 管理界面。
- 风险：复杂度提前支付。

## 4. 最终决策

最终选择：

- 数据源：方案 A（中国食物成分表第 6 版 + 全球 USDA 近似值）。
- 管道：方案 D（构建期静态 JSON 管道）。

核心理由：

1. 中文食材覆盖是产品生死线，第 6 版 + 全球补充是唯一同时满足「中文完整 + 全球做法」的可行组合。
2. 数据诚实是产品原则之一（见 `PRODUCT.md` 产品原则 4），source 字段标注让数据可追溯。
3. 菜谱营养由食材推导（`data/recipes/*.json` 的 ingredients 带克数），避免手工计算 77 道菜营养，食材库更新自动生效。
4. 构建期 JSON 与 ADR-0001 单服务架构天然契合：seed 幂等导入，重启不丢数据。

为什么不选择其他方案：

- 方案 B（仅 USDA）：中文食材缺口不可接受。
- 方案 C（CNFOOD-241）：V3 AI 功能才需要，现在接入是提前复杂度。
- 方案 E（运行期迁移）：与单服务、零配置原则冲突，收益不存在。

## 5. 架构与实现约束

- 数据源头：`data/raw/china-food/`（第 6 版 OCR）+ `data/global_foods.json`（USDA 近似值，必须标注 `source`）。
- 菜谱源文件：`data/recipes/*.json`，格式见 `data/recipes/chinese.json`；ingredients 必须带克数 `amount_g`，营养由食材 × 克数推导。
- 数据管道入口：`scripts/build_data.py`，产物为 `data/processed/foods.json` 与 `data/processed/recipes.json`，不得手工编辑 processed 产物。
- 运行期只读：`api/app/seed.py` 幂等导入 processed JSON 到 SQLite；新增 / 修改数据必须「改源 → build → 重启」三步，禁止直接改库。
- 菜谱详情页在 `next build` 时读取 `data/processed/recipes.json` 生成（见 `Dockerfile` 阶段 1），新增菜谱必须重新构建镜像。
- 版权约束：第 6 版数据商用需购买授权；爬虫数据仅学习研究；`docs/03-数据方案.md` 第 5 节为合规基线。

## 7. 验收标准

- 全量数据可复现：`python scripts/build_data.py` 幂等，产物 diff 为空（同输入同输出）。
- `data/processed/foods.json` 含 1741 条食材，每条标注来源；`data/processed/recipes.json` 含 77 道菜谱。
- 菜谱营养与「食材 × 克数」推导一致：修改食材库营养值后重新 build，受影响菜谱营养自动变化。
- seed 重复执行不产生重复数据、不报错。
- `pytest api/tests -q` 全绿。

## 8. 后果与风险

### 正面影响

- 营养数据可追溯、菜谱营养自动推导，维护成本低。
- 数据管道与单服务架构一致，运行期零数据依赖。

### 负面影响和代价

- 新增菜谱需要重新 build + 重启（或重建镜像），操作链路比运行期管理长。
- OCR 识别可能存在个别数值误差，需要抽检。
- 第 6 版数据商用受限。

### 持续跟踪风险

- [ ] 菜谱 / 食材扩充时，格式不一致导致 build 失败（保持 `data/recipes/chinese.json` 为格式基准）。
- [ ] 是否需要运行期数据管理（出现时重新评估方案 E）。
- [ ] 商用计划确定时，数据源合规切换（授权 / USDA 开源替代）。

## 9. 复盘

- 预期目标是否达成：达成。数据可追溯、菜谱营养自动推导、管道简单可复现。
- 实际收益和成本：管道开发一次，之后 77 道菜谱与 1741 条食材均为「改 JSON → build」完成，无迁移脚本负担。
- 哪些假设被证明错误：暂无。
- 是否需要新建 ADR 替代当前决策：需要时——若产品进入商用阶段（数据源合规切换）或出现运行期数据管理需求。
