# 技术方案

## 1. 架构（单服务，刻意保持简单）

```
[ 单个 FastAPI 服务 :8000 ]
   ├── /api/*         营养计算 / 推荐 / 菜谱 / 用户 API
   ├── /*             前端静态文件（web/out，next build 产物，无 Node 运行时）
   └── SQLite         单文件数据库（var/chisha.db，零配置）
   [数据管道：python scripts/build_data.py]
```

- 一个 Docker 容器（多阶段构建：Node 构建前端 → Python 运行时），`docker compose up -d --build` 即起。
- 数据库用 SQLite：单文件、零配置、好备份；模型使用通用 JSON 类型，`DATABASE_URL` 环境变量可切回 PostgreSQL。
- 前端 Next.js `output: export` 纯静态导出，菜谱详情页构建时读 `data/processed/recipes.json` 生成。
- 端口：8000（前端与 API 同源，无需 CORS / 多端口）。

## 2. 技术栈

- 前端：Next.js 15 + TypeScript + 自绘 SVG 图标 + 纯 CSS 设计系统（见 `DESIGN.md`）
- 后端：FastAPI（SQLAlchemy + SQLite）
- 数据管道：Python（json），`scripts/build_data.py`
- 设计规范：[impeccable](https://github.com/pbakaus/impeccable)（本地开发工具，不入库），用 `node .codex/skills/impeccable/scripts/detect.mjs <url|file>` 检测 AI 味

## 3. 推荐算法（规则打分）

```
score(recipe, user) =
  0.45 × 热量匹配 + 0.30 × 蛋白质匹配 + 0.15 × 目标标签匹配
  + 0.05 × 菜系偏好 + 0.05 × 多样性（避免同菜系连续）
```

- 先硬性过滤：过敏原 / 忌口
- 按早 / 午 / 晚 / 加餐各出 Top 3，页面标注「任选其一」

## 4. API（草案已实现）

```
POST /api/plan                  # 身体档案 + 目标 → 每日目标 + 分餐推荐
GET  /api/recipes?meal=&cuisine=&tag=&q=
GET  /api/recipes/{id}          # 菜谱详情（食材 / 步骤 / 营养 / 技巧）
GET  /api/foods?q=              # 食材营养查询
GET  /api/health
```
